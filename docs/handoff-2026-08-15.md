## Defect 1 — the assistant does not recognise a product unless it is spelled exactly

**Evidence, from the real conversation:**

| User said | Assistant answered |
|---|---|
| `atlas ziko ngapi?` | "Sina rekodi ya Atlas — haijawahi kuhesabiwa wala kuingizwa/kuuzwa mfumoni." |
| `atlasi ziko ngapi` | "Atlasi zimebaki 14." |

The stock count for `atlasi` had been saved **two minutes earlier**. One missing
vowel and the assistant claims the product does not exist. It then compounded it:
asked about profit on "atlas" it said it had *neither* a stock count *nor* a
buying cost — the first half of which was simply false.

**Root cause.** `private.product_key()` (migration `0091_canonical_product_key`)
normalises case, edge punctuation and inner whitespace, and **deliberately does no
stemming or fuzzy matching**. That was the right call for *writes* — merging
"daftari" into "daftari kubwa" would corrupt a ledger — but it was wrongly applied
to *reads* too. A read that finds nothing costs nothing to retry; a write that
merges two products silently is unrecoverable.

**What to build.** Asymmetric matching:

- **Reads** (stock on hand, profit, price lookups, "X ziko ngapi"): match loosely.
  Swahili noun classes make the ending unstable — `atlas`/`atlasi`,
  `kitabu`/`vitabu`, `kalamu` (invariant), `daftari`/`madaftari`. Try, in order:
  exact key → key with a trailing vowel added/removed → `ki-/vi-`, `m-/mi-`,
  `ji-/ma-` class pairs → trigram similarity (`pg_trgm`, threshold ~0.45) over
  that company's catalogue only.
- **When the match is not exact, say which product you answered about**:
  "Atlasi zimebaki 14" — not silently. If two candidates tie, ask.
- **Writes stay exact.** A stock count or a cost for an unrecognised name must
  keep asking, never guess.

`company_product_catalog(p_from, p_to, p_include_archived)` is the single source
of product names for a company; build the resolver on top of it. Watch out:
`ya`/`za`/`wa`/`cha` are **parts of product names here** (`nguvu ya sala`,
`rosali ya maria`, `kitabu cha hesabu`) — stripping them as connectives has
already broken this code once.

## Defect 2 — a comma-separated list of sales records the wrong amount

**Evidence:**

> User: `nimeuza daftari 5 kwa 7500, kalamu 3 kwa 1500`
> Assistant: *Aina: Mauzo · Maelezo: "daftari 5 kwa 7500, kalamu 3" · Jumla:* **TSh 1,500**

It should be **two lines totalling TSh 9,000**. Instead it took the last number as
the whole total and swallowed the first sale into a description string. If the
owner had answered NDIYO, the day's takings would be understated by 7,500 with no
trace that anything was lost.

**This is the highest-priority defect. It silently destroys money.**

**Root cause.** `parseDailyRecord` in
`supabase/functions/_shared/whatsappDailyRecords.ts` matches a trailing
`kwa <amount>` against the whole string, so the last amount wins and everything
before it becomes the description. `parseDailyRecordBatch`
(`whatsappDailyRecordBatch.ts`) splits on **newlines**, so a comma-separated list
never reaches it.

**What to build.** Teach the batch path about comma/`na`-separated sale items on a
single line — `<product> <qty> kwa <amount>` repeated. Then make the failure loud
rather than quiet: **if the parsed line totals do not account for every number in
the message, refuse and show what was not understood.** Prior art for the shape of
that refusal is in `whatsappStockBatch.ts` (`unreadable[]`, listed back, never
dropped) and `whatsappCostBatch.ts`.

Note the interaction with the mixed-topic splitter below: a comma is a cut point
there, but non-question pieces are glued straight back together, so a list of
goods is passed through untouched. Keep that property — there is a test for it.

## Defect 3 — the assistant gives up instead of saying what it is missing

**Evidence:** `zikiuza atlasi zote nitakuwa na faida ya shingapi` →
"Samahani, sikuweza kukamilisha jibu hilo sasa. Jaribu tena baada ya muda mfupi."

The same question about "atlas" a minute earlier produced a *good* answer that
named exactly what was missing (no stock count, no buying cost) and what to send
to fix it. So the machinery can do this; it failed intermittently — most likely
the bounded tool loop ran out of steps or the provider timed out.

**What to build.** A "hypothetical profit" question is answerable deterministically
whenever the pieces exist: `on_hand × (selling price − unit cost)`. Stock on hand
is `company_stock_on_hand` (0093), the retail/wholesale prices are
`product_selling_prices` (0098), the cost is `product_costs`. Add it as a first-class
read tool so it does not depend on the model improvising, and when a piece is
missing, **name the missing piece** — never "try again later".

## Facts that cost real time to learn — do not rediscover them

- Supabase Edge Function **HTTP 546 = worker resource limit** (CPU as well as wall
  clock). A killed worker writes **nothing**, so the receipt stays in "Processing"
  for ever and the upload is lost. That is why QR decoding and TRA verification
  live in `whatsapp-worker` **after** `extract-receipt` has saved, not inside it.
- `verify.tra.go.tz` sets **no cookie**. The flow is `GET /<CODE>` then
  `GET /Verify/Verified?Secret=HH:MM:SS`; the portal keys the session by caller.
  Verified with curl against an empty cookie jar.
- `now()` is frozen per transaction; `clock_timestamp()` advances. This has caused
  ties in `product_costs` ordering and in notification ordering — twice.
- This Tailwind theme has **no `brand` colour token**; semantic red is `red-600`,
  not `rose-600`. Fonts are Outfit (sans) and Lora (`font-display`). Role colours
  are CSS vars only (`--role-worker`, `--role-accountant`, `--role-admin`).
- All UI copy lives in `src/i18n/sw.ts`. Do not hardcode strings in components.
- Shell command substitution on this machine has mangled template literals and
  parentheses repeatedly. Edit files with the editor tool, not with shell one-liners.
