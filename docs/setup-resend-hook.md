# Wiring the Resend "Send Email" Auth Hook

Supabase Auth can call a custom edge function instead of sending emails itself.
Risip uses the `send-email` function backed by Resend for all transactional email
(OTP confirmation, password reset, magic link, etc.).

This is a **one-time manual step** — it can't be done from code or CLI.

---

## 1. Prerequisites

| What | Where to get it |
|---|---|
| Resend API key | <https://resend.com/api-keys> — create a key with **Sending access** |
| Verified From domain (production) | <https://resend.com/domains> — add and verify your domain |
| Supabase project deployed | migrations applied, edge functions deployed |

For smoke-testing you can skip the verified domain and let `RESEND_FROM` fall back
to `"Risip <onboarding@resend.dev>"`. Resend's sandbox only delivers to the account
owner's inbox.

---

## 2. Deploy the edge function

```bash
# From the project root — requires supabase CLI logged in
supabase functions deploy send-email --no-verify-jwt
```

> `--no-verify-jwt` is required: Supabase Auth does **not** attach a JWT to hook
> calls. Authenticity is proved instead by an HMAC signature (standard-webhooks).

---

## 3. Set edge function secrets

```bash
supabase secrets set \
  RESEND_API_KEY="re_xxxxxxxxxxxxxxxxxxxx" \
  RESEND_FROM="Risip <noreply@yourdomain.co.tz>"
```

`SEND_EMAIL_HOOK_SECRET` is generated by Supabase in step 4 and set afterwards.

---

## 4. Wire the hook in Supabase Dashboard

1. Open your project at <https://supabase.com/dashboard>
2. Go to **Authentication → Hooks** (left sidebar, under Auth)
3. Find **"Send email"** and click **Edit hook**
4. Set the hook type to **"Supabase Edge Functions"**
5. Choose the function **`send-email`** from the dropdown
6. Click **Generate a new secret** — copy the value (it looks like `v1,whsec_...`)
7. Click **Save**

Now set that secret in the function environment:

```bash
supabase secrets set SEND_EMAIL_HOOK_SECRET="v1,whsec_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

---

## 5. Enable email confirmations (production only)

In `supabase/config.toml`, when you're ready for production:

```toml
[auth.email]
enable_confirmations = true   # change from false → true
```

Then push the config:

```bash
supabase db push   # or deploy via CI
```

For local dev, `enable_confirmations = false` means users land straight in
without a verification step — keep this as-is during development.

---

## 6. Verify it works

1. Sign up a new user via the app
2. Check the Resend dashboard → **Emails** to confirm delivery
3. Check edge function logs: **Dashboard → Edge Functions → send-email → Logs**

If the signature verification fails (`invalid signature 401`), the hook secret
doesn't match. Re-generate and re-set.

---

## Environment variable summary

| Variable | Set in | Value |
|---|---|---|
| `RESEND_API_KEY` | Edge Function secrets | Resend API key |
| `RESEND_FROM` | Edge Function secrets | `"Name <email@domain.com>"` |
| `SEND_EMAIL_HOOK_SECRET` | Edge Function secrets | `v1,whsec_...` from Dashboard |
| `VITE_SUPABASE_URL` | `.env.local` | `https://<ref>.supabase.co` |
| `VITE_SUPABASE_ANON_KEY` | `.env.local` | anon key (safe to ship to browser) |

The `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` is used only for local Supabase
CLI commands. It must **never** appear in any `VITE_*` variable or be shipped
to the browser.
